# 산출물 작성 (proposal-writer)

## 전제

- `rubric.json`과 `02_아이디어.md`(사용자가 선택한 아이디어)가 있어야 한다.
- 지정 양식이 `00_공고/`에 있으면 그 목차를 그대로 따른다. 양식이 우선이다.

## 1. 구조 잡기

지정 양식이 없으면 산출물 종류에 맞는 기본 구조를 쓴다.

| 종류 | 기본 구조 |
|---|---|
| 기획서·제안서 | 개요(한 줄 요약) → 배경·문제(근거) → 해결방안 → 차별성 → 실행계획·실현가능성 → 기대효과(정량+정성) → 결론 |
| 개발·해커톤 | 문제 → 솔루션 → 핵심 기능 → 기술 구조 → 데모 시나리오 → 확장 계획 |
| 발표 대본 | 훅(30초) → 문제 → 해결 → 데모/근거 → 임팩트 → 마무리 한 문장 |
| 수기·에세이 | 주제문 → 구체적 경험 장면 → 깨달음·변화 → 공모 주제와의 연결 |
| 영상(홍보·UCC·데모) | 훅(첫 5초) → 문제 → 해결·핵심 장면 → 근거·임팩트 → 마무리 메시지 → (필수 자막·로고) → **6장 참고** |

## 2. 심사기준 매핑 (필수)

작성 전에 목차 각 절이 어떤 심사항목을 담당하는지 표로 만든다.
**배점이 큰 항목일수록 분량과 근거를 더 배치**하고, 매핑되지 않은 심사항목이 없게 한다.

## 3. 작성

- `03_초안.md`에 쓴다. 수정본은 `03_초안_v2.md`처럼 새 파일로 남긴다.
- 분량 제한을 지킨다 (페이지 제한이면 A4 1쪽 ≈ 한글 1,500~1,800자로 추정하고 그 사실을 알린다).
- 수치·사실은 `01_리서치.md`의 출처가 있는 것만 쓴다.
- 첫 페이지(또는 첫 문단)에 아이디어의 핵심과 차별점이 바로 보이게 한다. 심사위원은 앞부분을 가장 집중해서 읽는다.
- 전문용어는 심사위원이 비전문가일 수 있다고 가정하고 풀어 쓴다.
- 공모전이 AI 사용 표기를 요구하면 표기 문구 위치를 안내한다.

## 4. 심사 루프

초안이 완성되면 심사위원 두 명에게 **차례로** 채점을 맡긴다. 동시에 띄우지 않는다.

1. **judge (Claude)**: 프롬프트에 rubric.json 경로와 초안 경로를 넣는다. 결과를 `04_심사결과.md`에 저장한다.
2. **judge-codex (Codex)**: judge가 끝난 뒤 띄운다. 프롬프트에는 공모전 폴더 경로와 초안 파일 이름만 넣고,
   **judge의 점수·의견은 절대 알려주지 않는다**(독립 채점). 결과는 `04_심사결과_codex.md`에 저장된다.
   - judge-codex가 실패하면(미설치·로그인·한도 초과 등) 그 사실을 사용자에게 한 줄로 알리고 judge 결과만으로 진행한다.
3. **종합**: 두 결과를 합쳐 `04_심사결과.md` **맨 위**에 아래 표를 넣는다.

   ```
   ## 교차 채점 요약
   | 항목 | 배점 | Claude | Codex | 평균 | 비고 |
   |---|---|---|---|---|---|
   | ... | 30 | 24 | 18 | 21 | ⚠️ 의견 갈림 |
   | 총점 | 100 | .. | .. | .. | |
   ```

   - 두 점수 차이가 **해당 항목 배점의 20% 이상**이면 비고에 "⚠️ 의견 갈림"을 표시한다 (예: 배점 30점 → 6점 차 이상).
   - 의견 갈림 항목이 있으면 수정 전에 항목마다 두 심사위원의 근거를 짧게 정리해 **사용자에게 어느 쪽을 따를지 묻는다.**
4. **고칠 목록**: 표 아래에 수정 목록을 둔다.
   - **둘 다 지적한 약점**을 맨 앞에 두고, 그다음 한쪽만 지적한 약점을 점수 상승폭 큰 순으로 둔다.
   - 의견 갈림 항목은 사용자가 고른 쪽의 의견을 따른다.
5. 목록을 반영해 수정 → 다시 1~4단계로 채점한다. **수정 루프는 최대 2회.**
6. 2회 후 남은 약점은 사용자에게 목록으로 넘긴다.

## 5. 최종 형식

- 제출 형식으로 변환할 때는 document-skills의 해당 스킬을 쓴다: Word는 `docx`, PDF는 `pdf`, 발표자료는 `pptx`, 예산표 등은 `xlsx`.
- 포스터·카드뉴스 같은 시각물은 `canvas-design`, 웹 데모·랜딩 페이지는 `frontend-design` 스킬을 쓴다.
- **한글 지정 양식(HWPX)**: `hwp` MCP(hwp-mcp)로 양식의 **복사본**을 만들어 칸을 채운다. `00_공고/`의 원본 양식은 그대로 둔다.
  - 채운 뒤에는 렌더링으로 페이지를 확인한다(표 깨짐, 칸 넘침, 분량 초과, 빈 칸).
- **양식이 구형 `.hwp`면**: 같은 공모전 페이지(첨부파일, 공지사항)에서 HWPX 양식부터 찾아본다.
  없으면 원본 양식과 같은 목차·항목 순서로 새 HWPX를 만들어 채우고, 렌더링으로 확인한다.

## 6. 영상 산출물 (Remotion)

제출물에 영상(홍보영상, UCC, 해커톤 데모, 발표영상)이 있으면 Remotion 스킬로 만든다.

1. **규격 확인** – rubric.json에서 길이, 해상도·비율, 파일 형식·용량, 자막 필수 여부, 로고·문구 삽입 조건을 확인한다.
   - **AI 사용 규정이 "금지"이거나 "직접 촬영 영상만 허용"이면 영상 제작을 시작하지 말고 사용자에게 먼저 알린다.**
2. **스토리보드 먼저** – `06_영상/스토리보드.md`에 장면별 표를 만들고 사용자 확인을 받은 뒤에 코드를 만든다.

   | 장면 | 시간(초) | 화면 | 자막·내레이션 | 담당 심사항목 |
   |---|---|---|---|---|

   - 장면마다 어떤 심사항목을 담당하는지 적고, 배점 큰 항목을 앞쪽 30초 안에 보여준다.
3. **제작** – `/remotion-best-practices` 스킬을 따른다. 프로젝트는 `06_영상/` 안에 만든다.
   - 자막은 `/remotion-captions`, 지도·경로 애니메이션은 `/remotion-maps`를 쓴다.
   - 사용자가 준 촬영본·이미지가 있으면 그것을 우선 쓰고, 없는 부분만 텍스트·도형·차트 애니메이션으로 채운다.
4. **미리보기** – `/remotion-studio`로 사용자에게 확인받고 수정한다. 수정은 최대 2회.
5. **렌더링** – `/remotion-render`로 규격에 맞는 mp4를 `06_영상/`에 만든다. 길이·해상도·용량을 다시 확인한다.
6. **저작권** – 음원·이미지·폰트는 출처와 라이선스를 `06_영상/출처.md`에 기록한다. 라이선스가 불분명한 소스는 쓰지 않는다.
7. **라이선스** – 처음 쓸 때 `/remotion-license`로 개인·소규모 팀 무료 조건에 해당하는지 확인해 사용자에게 알린다.
- Remotion 스킬이 설치되어 있지 않으면, 사용자에게 `npx skills add remotion-dev/skills` 설치를 안내하고 스토리보드까지만 진행한다.
